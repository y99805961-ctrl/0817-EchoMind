# 技术故障与错误码

## 1. 文档适用范围

本文用于 App、网页、API 或服务端出现加载失败、登录异常、崩溃、超时、接口错误、限流、Webhook 异常等技术问题。账户安全相关验证请结合《账户登录与安全》。

## 2. 通用排查原则

技术故障处理遵循“先确认范围，再做最小复现”的原则。

需要确认：

- 哪个平台：App、Web、API；
- 操作步骤；
- 发生时间；
- 是否每次出现；
- 是否只影响一个账户；
- 网络环境；
- App 或浏览器版本；
- 错误码；
- request_id / trace_id（如有）。

不要在没有证据时直接让用户“卸载重装”，因为这可能丢失本地状态且无法定位根因。

## 3. HTTP 401

401 表示请求没有通过身份认证。常见原因：

- access token 过期；
- token 缺失；
- token 格式错误；
- 会话已被注销；
- 账户安全策略使旧凭证失效。

排查：

1. 确认用户是否仍能正常登录；
2. 刷新 token 或重新登录；
3. API 场景确认 `Authorization` 头；
4. 检查客户端时间是否异常；
5. 若大量用户同时出现，升级身份服务。

## 4. HTTP 403

403 表示身份可能已经识别，但当前请求没有权限。

常见原因：

- 账户权限不足；
- 资源属于其他用户或租户；
- 风控临时限制；
- 管理员策略；
- API scope 不包含目标权限。

不要把 403 和 401 混为一谈。401 关注“你是谁”，403 更关注“你有没有权限做这件事”。

## 5. HTTP 429

429 表示请求频率超过限制。

处理：

- 降低请求频率；
- 遵守 `Retry-After`；
- 使用指数退避；
- 避免无意义循环重试；
- API 客户端检查是否重复发送；
- 用户验证码场景不要连续点击。

如果单个普通用户在正常操作下持续触发 429，需要检查限流配置是否异常。

## 6. HTTP 500

500 表示服务端内部错误。

客户端可以：

- 重试一次；
- 保留 request_id；
- 记录发生时间；
- 避免连续大量重试。

如果 500 持续出现，应升级服务端排查，不应该长期要求用户清缓存。

## 7. HTTP 502 / 503 / 504

- **502**：上游服务返回异常；
- **503**：服务暂时不可用；
- **504**：网关等待上游响应超时。

这些错误通常更接近服务端或依赖故障。如果多个用户同时出现，优先查看系统状态和依赖服务。

## 8. App 崩溃

排查信息：

- App 版本；
- 系统版本；
- 设备型号；
- 崩溃发生页面；
- 是否稳定复现；
- 最近是否升级；
- 是否在特定网络下出现。

用户可尝试：

1. 完全关闭 App 后重新打开；
2. 检查是否有新版；
3. 重启设备；
4. 确保设备剩余存储充足。

只有确认缓存损坏可能相关时，才建议清理缓存。卸载前应提醒可能需要重新登录。

## 9. 网页加载失败

排查：

- 是否只有一个页面；
- 浏览器版本；
- 无痕模式是否正常；
- 是否启用了会拦截脚本的扩展；
- 网络是否可以访问其他页面；
- 控制台是否有明确错误。

如果同一账户在多个浏览器都失败，更可能是服务端或账户数据问题。

## 10. 网络超时

常见错误：

- `NETWORK_TIMEOUT`
- `CONNECT_TIMEOUT`
- `READ_TIMEOUT`

需要判断是：

- 用户本地网络；
- DNS；
- CDN；
- API 网关；
- 后端服务；
- 第三方依赖。

一次超时可以重试；连续超时应该停止盲目重试并保留诊断信息。

## 11. Webhook 异常

Webhook 常见问题：

- endpoint 返回非 2xx；
- 签名验证失败；
- 接收方处理超时；
- 重复事件；
- 事件顺序与预期不同。

消费者应该使用 `event_id` 做幂等处理，不要假设 Webhook 只发送一次。

如果签名失败，需要检查：

- secret 是否正确；
- 原始请求体是否在验证前被修改；
- 时间戳容差；
- 是否使用了错误环境的 secret。

## 12. API 鉴权

API 调用应使用正确的 API Key 或 OAuth token。

客服和技术支持不能让用户在公开聊天中发送完整 API Secret。建议只提供：

- Key 前后少量脱敏字符；
- request_id；
- 错误码；
- endpoint；
- 时间。

## 13. 系统维护

计划维护期间，应提供：

- 开始时间；
- 预计结束范围；
- 受影响功能；
- 可用替代方案；
- 状态更新渠道。

如果没有可靠恢复时间，不应编造精确恢复分钟。

## 14. 服务大面积故障

识别信号：

- 多个用户同时报告；
- 监控错误率上升；
- P99 延迟显著增加；
- 关键依赖不可用；
- 同一错误码集中出现。

此时不应把每个用户都当成独立设备问题处理，应转入 incident 流程。

## 15. 技术支持需要收集的信息

推荐字段：

- `user_id`（脱敏或内部标识）
- `request_id`
- `trace_id`
- 时间戳和时区
- endpoint / 页面
- 错误码
- 客户端版本
- 操作步骤
- 是否可复现

避免收集无必要的敏感数据。

## 16. 客服处理 SOP

### 401
先重登/刷新凭证，再判断是否身份服务异常。

### 403
检查权限和资源归属。

### 429
停止高频重试，尊重退避。

### 500/502/503/504
保留 request_id，判断是否系统性故障。

### App 崩溃
收集版本和复现步骤，不要第一句就要求卸载。

## 17. 人工升级条件

- 同一错误影响多用户；
- 500 系列错误持续超过 10 分钟；
- 关键接口 P99 明显恶化；
- Webhook 持续失败且业务数据可能丢失；
- 用户可稳定复现 App 崩溃；
- request_id 显示服务端未处理成功；
- 涉及数据错误、账户串号或权限越权；
- 出现安全相关异常。

## 18. 常见问题

### 401 和 403 有什么区别？
401 更偏认证失败，403 是已经识别身份但没有权限。

### 500 需要用户一直刷新吗？
不需要。少量重试可以，持续 500 应保留 request_id 并由服务端排查。

### Webhook 为什么会重复？
可靠消息系统可能重复投递，接收方应通过 event_id 做幂等处理。
